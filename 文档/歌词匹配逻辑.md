# 歌词下载/匹配逻辑（先后顺序）

## 一、单曲流水线（严格按序）

| 步 | 动作 | 判定/说明 |
|---|---|---|
| 0 | 预检查 | 已有 .lrc/.LRC/双扩展名/内嵌歌词 → 跳过；标题命中「伴奏/纯音乐/Instrumental/KTV」→ 跳过 |
| 1 | 取元数据 | 优先读标签 title/artist/album/duration；缺失再从文件名解析（`01 - 歌手 - 歌名`） |
| 2 | 归一化 | NFKC、去括号内容、去 feat/remix/live、只留字母数字中文 |
| 3 | 快源搜索（并行） | 网易云 / QQ / 酷狗，单源 8 秒超时 |
| 4 | 候选合并 | 去重（source+id），保留原始时长 |
| 5 | 打分排序 | 歌名 60/35/−25；歌手 30/20/−15；时长 ±2s +30、±5s +18、±10s +6、>10s −25 |
| 6 | 是否够好 | 最高分 ≥ minScore+20 → 跳过慢源，直接进第 8 步 |
| 7 | 慢源兜底 | LRCLIB（12~15s），合并后重排（它只在快源不给力时才问） |
| 8 | 取歌词 | 对排序前 3 个「还没歌词」的候选并行 resolve（单源 15s） |
| 9 | 重排 | 有歌词的候选再按分数排序，取第 1 |
| 10 | 阈值闸门 | 分数 < minScore（默认 55）→ 标记「未匹配」，不写盘 |
| 11 | 歌词清洗 | 去 BOM/HTML 实体、统一换行、校验时间轴；无时间轴的纯文本按配置处理 |
| 12 | 补头 | `[ti:][ar:][al:][by:musicTB][offset:0]`（已有头则不动） |
| 13 | 写盘 | 按写入方式：仅 .lrc / 仅内嵌 / 两者；.lrc 已存在且「保留已有」→ 跳过 |
| 14 | 回写状态 | done / skip / noperm / nomatch + 来源 + 分数 + 时间 |
| 15 | 重试策略 | 网络类失败串行重试 1 次；某源连续失败 2 次 → 冷却 5 分钟 |

## 二、源优先级

1. **网易云** — 中文命中率最高，返回逐行 LRC
2. **QQ 音乐** — 同级别，欧美曲库强
3. **酷狗** — 需要 hash→候选→下载 三步
4. **LRCLIB** — 慢（实测 10~20s），只在兜底时使用；英文/冷门曲强
5. **酷我** — 实验性，默认关闭

> 优先级不是硬性串行：1~3 是**并行**搜索，谁分高用谁。4 是兜底。

## 三、批量任务

- 并发 2（可设 1~6），每个源调用间隔 250ms
- 单曲最坏预算：8s（快源）+ 15s（慢源兜底）
- 断点续跑：状态写进曲库，重启后从「缺失」继续，不会重头来
- 停止：点「停止」在当前曲目结束后退出，不丢已写入结果

## 四、写盘顺序与失败隔离

1. 先写 `.lrc`（可逆、零风险）
2. 再写内嵌标签（若开启「改标签前备份音频」会先复制整份）
3. 单曲失败只记录，不影响后续；失败原因分类：无权限 / 未匹配 / 网络 / 标签写入失败

## 五、三个可调参数

- `minScore`（默认 55）：低于此分不写，宁可空着也不写错
- `lyricFetchTop`（默认 3）：只给分数最高的 3 个候选取歌词，控制请求量
- `sourceTimeoutMs`（默认 15000）：单源超时

## 六、我建议再加的两条（待你确认）

1. **官方歌词优先**：若飞牛音乐库里已有内置歌词（数据库里的），先读它，避免重复下载
2. **同名不同版保护**：时长差 >10s 的候选直接判负，防止「Live 版」覆盖「录音室版」
